Cameroon Catering Service

A web-first catering marketplace for Cameroon. Customers find and compare verified caterers for weddings, funerals, birthdays, church, school and office events, request quotes, and pay a deposit by Mobile Money. It is a booking and quotation platform, not a food-delivery app, and it earns a commission on each completed booking.

Status as of 19 September 2026 · Front end complete on seed data · No backend, no auth, no payments · Not deployed

What exists today. A complete, bilingual, mobile-first Next.js 14 front end: 17 routes plus a 404 page, 47 source modules, about 5,700 lines of TypeScript and TSX. It builds clean and typechecks clean. Every screen in the customer, caterer and admin journeys is drawn and navigable, and the numbers on those screens are computed rather than hardcoded — commission, deposit, per-guest totals and add-on scaling all run through real functions in src/lib.

What does not exist. Anything behind the screen. There is no database, no authentication, no payment integration and no persistence of any kind. Every piece of state in this application lives in React component state and is gone on refresh. A quote request is not sent anywhere. A deposit is not collected. An approved caterer is not approved — the row simply disappears from a list until the page reloads. This is deliberate and documented, but it is the difference between a demonstrable product and a usable one.

"Built" and "working" are different words on this page. Built means the code exists, typechecks, and produces the screen it is supposed to produce. Working would mean a real person completed the action and the result survived. Nothing on this project is Working yet, because there is no server to survive into. The counters below separate the two on purpose, and they should stay separated as the backend lands.

Verified on 19 September by running it. Four facts here are results, not claims. npm run build succeeds on Next.js 14.2.15 and emits 18 route entries. tsc --noEmit exits clean. The EN and FR dictionaries are at exact parity — 199 keys each, with no key present in one language and missing from the other. And one negative result: npm run lint does not work. The repository has no ESLint configuration and no ESLint dependency, so next lint drops into its interactive first-run setup prompt and never lints anything. Both README.md and CLAUDE.md list it as a normal command. It has never run.

The project documentation is behind the code. CLAUDE.md lists "build a working leave-a-review form" and "a real signup/profile-builder flow" as things still to do, and its page inventory stops at twelve routes and the 404. Both of those screens were in fact shipped in commit ed3827d, along with /login, /signup and /offers. Five routes exist that the project's own documentation does not mention. That is not a defect in the code, but it is the reason this status page was needed: the source of truth had drifted.

One architecture rule is being broken at scale. CLAUDE.md requires every user-facing string to go through useI18n().t(key) with EN and FR entries in the dictionary. There are 94 inline fr ? "…" : "…" ternaries across 9 files that bypass it entirely, concentrated in the newer pages — /caterers/join alone has 27. The pages still render correctly in both languages, so nothing is visibly broken; what is lost is the single place to change a translation, and the ability to add a third language without touching every file. The dictionary itself remains healthy and at parity, which is why this is In progress rather than Broken.

Payments are the gating decision, not the gating code. The checkout screen already collects the method, the MoMo number and the event date, and computes the 30% deposit against the package total. What it cannot do is call MTN or Orange, and that is not primarily an engineering problem: collection APIs for both require a registered Cameroonian business entity, a merchant account and KYC. Until that exists, the integration cannot be tested even if it were written. See Documentation/PAYMENTS.md.

No deployment. vercel.json pins the framework to Next.js and the application is a static-friendly build with only one server-rendered route, so hosting is straightforward. But no deployment has been made or confirmed from here, and there is no environment configuration to make yet, because there are no secrets to configure. The first real deployment should wait until there is a backend for it to talk to, or be published knowingly as a public demo.

Zero automated tests. Not one. On a project whose money model is a percentage of a booking total, the commission and deposit arithmetic in src/lib/format.ts is the first thing that should have a test around it, and it is a small, pure, dependency-free function — perhaps thirty minutes of work for the highest-value coverage on the project.

1 · What this project is

In Cameroon, catering for a wedding, a funeral or a church event is arranged through WhatsApp groups, phone calls and personal recommendation. Prices are quoted verbally, there is no record of what was agreed, deposits change hands informally, and a customer outside the recommender's network has no way to compare one caterer against another.

This platform replaces that with a structured booking and quotation flow: a searchable directory of verified caterers, packages priced per guest in FCFA, a written quote, a deposit paid through Mobile Money, and a review that can only be left against a completed booking. The platform takes a commission on each successful booking.

It is explicitly not a food-delivery application. Nothing in the product moves food; it moves agreements about food.

The change being made

Today:   Customer → WhatsApp group → whoever answers → verbal price → cash deposit
Proposed: Customer → Marketplace → compare verified caterers → written quote → MoMo deposit

4 · Architecture

Technical direction as built

  • Next.js 14, App Router, TypeScript, Tailwind. Three runtime dependencies in total: next, react, react-dom. Nothing else ships to the browser.
  • UI in src/components, data in src/data, domain logic and types in src/lib. The separation is kept — no component reaches past the data helpers, and no data module imports a component.
  • Interactive pages are client components. The five that read useSearchParams — browse, quote, offers, checkout and review — are each split into a thin server page.tsx that wraps a *Client.tsx in <Suspense>, which is what App Router requires.
  • One dynamic route. /caterers/[id] is server-rendered on demand; every other page, and the 404, prerenders as static content. Once there is a database, that route is the natural first place to fetch from.
  • The seed layer is the only seam. Every page reads through the exported helpers in src/data — getCaterer, reviewsFor, catererBookings, totalCommission. Replacing those function bodies with queries is most of the backend migration.

Why the types came first

src/lib/types.ts is not a convenience file for the UI. It was written as the eventual database schema — users, customers, caterers, bookings, quote requests, reviews, payments, messages, featured listings, subscriptions and add-on services — and the seed data was then written to satisfy it. The effect is that the prototype has already been forced to answer schema questions that are expensive to answer late: what a booking reference looks like, whether commission is stored per booking or derived, how availability is represented, and what a package is separate from a menu item.

The cost of that decision is that the types are ahead of the code in places. User, payments, messages, featured_listings and subscriptions are described in the type file and referenced in the README, but no screen persists any of them. That is intentional, and it is the map for the backend work rather than a claim about it.

Why no backend yet

Choosing Supabase or Firebase is a decision with a cost attached, and it is better made once the screens have settled what the data has to look like — which they now have. The analysis, with a recommendation, is in Documentation/BACKEND_DECISION.md. It is a decision, not a research task; the research is done.

6 · Explicitly outside the MVP

  • Food delivery and logistics. Never in scope.
  • Real photographs. Placeholder art is deliberate until a storage bucket exists; it keeps the app dependency-free and fast.
  • In-app messaging. Replaced in the MVP by WhatsApp deep links and a contact form, which is where these conversations actually happen in Cameroon.
  • The expansion services surfaced in the UI — photographers, DJs, lighting, cleanup, transport, full event planning — are a roadmap shown to caterers, not a built feature.
  • A third language. EN and FR cover the official languages; nothing else is planned.
  • Native applications. Web-first, mobile-first, and that is the whole distribution plan for the MVP.

9 · Open decisions for the owner

Five questions that engineering cannot answer for itself. Each one blocks work that is otherwise ready to start. The detail is in Documentation/OPEN_REQUESTS.md.

DecisionWhat it blocks
Supabase or FirebaseThe entire backend phase. Both fit; they differ in how the data is queried and how permissions are expressed. A recommendation with reasoning is written up and waiting.
Payment route — aggregator or directDeposit collection, and with it the revenue model. A direct MTN and Orange integration is cheaper per transaction and requires a registered business, a merchant account and KYC. An aggregator is faster to launch and takes a cut of a cut.
Launch commission rate, and who pays itCaterer recruitment and every price shown on the platform. The code defaults to 12% charged to the caterer; 10%, 15%, or splitting it with the customer are all supported by the constants but change the pitch entirely.
Launch city and first caterersA marketplace with no caterers has nothing to show. Douala and Yaoundé are the obvious candidates; whichever is chosen needs real caterers signed up before the platform is worth opening to customers.
Product name, domain and legal entityDeployment, the legal pages, and anything printed on a receipt. "Cameroon Catering Service" is a working title, and the terms and privacy pages are explicitly placeholders that must be professionally drafted before launch.

10 · Immediate next steps

In order. The first three are cheap, unblocked, and can be done today; the rest depend on decisions above.

  • Fix the lint setup. Add eslint and eslint-config-next and an .eslintrc, so the command both files already document actually runs. Then run it once and see what it says about 5,700 lines that have never been linted.
  • Test the money. formatFCFA, the 30% deposit rounding and the 12% commission are pure functions with no dependencies. A handful of assertions around them is the highest-value hour available on this project.
  • Reconcile CLAUDE.md with the code. Add the five undocumented routes to its page list, and move the review form and caterer onboarding out of the to-do list into a "simulated, needs a backend" section, where they honestly belong.
  • Decide the backend and create the schema from src/lib/types.ts. The types have already done the design work.
  • Make one flow real, end to end before making all of them real: quote request → stored → caterer notified → caterer replies. That single path exercises the database, auth and notifications together, and it is the flow the business runs on.
  • Then authentication, so the three dashboards stop being public URLs showing fixed demo users.
  • Then payments, once there is a merchant account to test against. Write the bank-transfer reference flow first — it needs no provider integration and it is what large weddings will actually use.
  • Close the two dead buttons. Featured listings and Premium are two of the four stated revenue streams and neither is clickable. Either wire them to billing or take them off the screen until they work.
  • Move the 94 inline ternaries into the dictionary before the string count grows. This gets harder every time a page is added.
